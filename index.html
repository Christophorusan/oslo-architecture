Understanding AI Agents with Harmonix

Signals · Audience Graph · Recommendations · Units · Memory · Connectors

Turns Codex and Claude Code into a company operator that learns who matters, what is working, and what should happen next

Architecture Spec

Oslo should not just run isolated tasks. It should behave like a company learning loop. The job is to watch the surfaces where Harmonix already operates, understand who is reacting, classify which accounts look like users versus partners, search for more people like them, track roadmap progress, recommend who to contact and why, and propose the content most likely to work next.

That changes the architecture. Instead of thinking about Oslo as a bag of scripts, think of it as an intelligence layer sitting under Codex and Claude Code. Reactions, replies, product milestones, partner conversations, roadmap state, and content performance all get written into one operating memory. From there, the system can score accounts, build lookalike lists, connect each opportunity to a roadmap moment, and explain the next best action with reasons.

Oslo has one operator, six departments, and four entry points. Codex and Claude Code are the primary entry points because they are the reasoning and review layer. Discord and Telegram are the chat surfaces where live signals and quick approvals happen. All four reach the same dispatcher. Dispatch should not only pick a skill. It should capture the signal, classify it, enrich it, score it, and route it to the right unit. The unit then runs Plan → Act → Verify, streams progress back, and writes episodic memory so the next run starts smarter.

Two model paths. Codex / Claude Code path: when you drive Oslo from one of these, the host model is already in the loop. It understands your input, emits a structured call, and Oslo runs the skill with no extra routing call. Chat path: when you drive Oslo from Discord, Telegram, X reactions, or a scheduled trigger, there is no host model. Oslo's dispatch handles routing itself through a fast deterministic ladder, falling back to a small LLM only for genuinely novel inputs. Why not put an LLM at the front of every dispatch like other agent frameworks? Because two LLMs in series, host model upstream plus dispatcher LLM, would do the work twice.

Oslo orchestrates with other bots. External agent systems are reached through read-only or read/write contracts following the open Agent2Agent (A2A) protocol hosted by the Linux Foundation, supported by Microsoft, Google, and AWS. Oslo never copies their state. The two systems share a contract, not a database.

Oslo's architecture has two layers. The data plane is the path every request takes: signal → classification → recommendation → unit action → memory update. The control plane is the configuration the data plane reads from on every request: a versioned skill registry, prompt registry, connector catalog, eval harness, and feature flags. Data plane runs constantly; control plane is loaded at boot and hot-reloaded on change. Detailed in Section 2 (Dispatch), since dispatch is the heaviest reader.

1. Signals

Signals are everything Oslo watches. Some come from operators driving Oslo directly. Others come from the world — engagement on a post, a deposit on the protocol, a scheduled trigger firing. All signals reach the same dispatcher.

Long-running handling is async-first: dispatch returns a job_id immediately and streams results back as they happen. A ninety-second skill does not block the IDE or the chat.

Operator-driven signals

Two of these come with their own model loaded — the host model in your coding agent does the natural-language interpretation. The other two are chat surfaces with no upstream model.

Claude Code is from Anthropic; Codex is from OpenAI. Different host models, same role to Oslo.

Codex — e.g. oslo bd.daily-leads --limit=50 from a terminal. Scripted runs, automation, scheduled jobs.

Claude Code — Oslo's tools appear in your coding session via an MCP server (Model Context Protocol — a standard interface for AI assistants to call external tools). Stdio for local mode, HTTP/SSE for hosted. Multi-step work where you want to read along.

Discord — slash command in a channel or @mention. Work that belongs in a shared log: outreach drafts, weekly briefs, anything the team should see.

Telegram — message the bot in plain language. Quick checks and phone approvals.

Non-operator signals

Signals that wake the dispatcher without a human typing:

  • X reactions — every like, reply, repost, quote on @harmonixfi posts. Treated as audience-graph input.
  • App activity — deposits, withdrawals, vault interactions on the Harmonix app. Treated as user-classification input.
  • Cron — scheduled timer (default UTC, per-skill timezone override). Daily and weekly skills run on cron.
  • Webhooks — URLs external services POST to when something happens (Stripe payment, GitHub PR merged, partner-side event).
  • Replay — re-run a past trace_id, optionally with a different model, prompt, or skill version. Used for debugging and prompt regression testing.

Note: Whether typed by a human or fired by a timer, every signal gets normalized into the same shape and handed to dispatch. The unit running at the other end never has to know where the signal came from.

2. Dispatch + Classification

The audience graph is where signals become usable company context. Dispatch normalizes the event, but this layer decides whether an account looks like a user, a partner, a prospect, a power user, or just noise. It enriches the profile, links it to similar accounts, and writes that relationship back into memory.

This is the Moneyball layer. Instead of trying to outwork larger teams, Oslo should out-select them. It should score which people matter, which roadmap moment they are closest to, and which opportunities deserve attention now.

Every input gets three IDs at parse time: trace_id (random, follows the request through every layer, replayable later), idempotency_key (deterministic, deduplicates retries), and capability_token (issued at run time, enumerates exactly what the skill can read, write, and call — checked at every boundary).

What classification adds

The Classify step is what makes dispatch more than a router. Before any skill runs, the dispatcher answers: who or what is this signal about? An X reaction goes through identity resolution — does the handle match a known user, a known partner contact, a lookalike candidate, or a stranger? An app event matches against the user table. A roadmap webhook matches against the current roadmap state. Classification writes its result onto the input itself, so by the time a skill receives the call, it already knows whether the signal is high-priority (a known partner replying) or background noise (a bot retweet). Skills don't reclassify — they trust the dispatcher's output.

What dispatch reads from the control plane

Dispatch is the heaviest reader of the control plane — the configuration the data plane consults but never writes to. On every request, dispatch reads from five components:

  • Skill Registry (versioned) — every skill the runtime knows about, with version numbers. Old versions stay queryable so replay can re-run any historical skill against any past input.
  • Prompt Registry — every LLM prompt named and versioned, separate from skill code. Editing a prompt does not require a redeploy. Prompt rollback is one revert away.
  • Connector Catalog — every external API connector available to skills, with declared cost, rate limit, and current health status. The catalog rejects skills that request connectors not present (or currently unhealthy).
  • Eval Harness — golden-test runner. Every skill ships with at least three test cases; CI runs the full suite on every change. Replay can also re-run last week's prod traffic against any new skill or prompt version and diff outputs — no skill or prompt change ships without this gate passing.
  • Feature Flags — turn skills on/off, route a percentage of traffic to a canary version, gate experimental connectors.

Keeping the two planes separate matters because the data plane needs to be fast and stable; the control plane needs to be flexible and frequently updated. Mixing them — hardcoded prompts inside skill code, connector configs scattered across files, no eval gate — is what turns small agent prototypes into systems no one can change without breaking.

The 4-tier resolver

Cheapest-first. Most inputs resolve without an LLM call.

  1. Slash — e.g. /oslo bd.daily-leads maps direct to skill ID.
  2. Channel + tag — e.g. @oslo refresh leads in #bd narrows to BD skills.
  3. Lunr index — keyword search over skill descriptions and triggers, deterministic.
  4. Small-model classifier — a small fast model returns {skill_id, args, confidence}. Free-tier inference is enough for routing; we don't burn paid frontier calls on classification. Below threshold → confirm-and-edit.

Streaming back

Skill progress events stream to the originating entry point as they happen — Discord typing indicator, Telegram message edits, Codex stdout, Claude Code partial MCP responses. The operator can also call oslo status <job_id> from any entry point or list active jobs with oslo jobs.

Note: When you drive Oslo from Codex or Claude Code, dispatch is trivial — the host model has already produced a structured tool call. The deterministic ladder (tier 1 / tier 2 / tier 3, with LLM fallback at tier 4) exists for chat surfaces (Discord, Telegram) where there is no host model upstream. Other agent frameworks (OpenAI Agents, Microsoft Agent Framework, LangGraph) put an LLM at the front of every dispatch regardless of source — for Oslo, that would mean running two LLMs in series (host model + dispatcher LLM) when one has already done the work.

3. Audience Graph

The audience graph is Oslo's model of who matters. It is the data structure underneath every BD outreach decision, every Marketing audience-targeting question, and every Ops priority call.

Three primary classifications, plus a graph of relationships between them:

  • Users — accounts that interact with the protocol (deposits, withdrawals, vault activity, app sessions). Identity-resolved across surfaces — the same person can have a handle on X, a wallet on chain, a Discord ID, a Telegram ID, and Oslo merges them.
  • Partners — accounts engaged in BD relationships. Includes warm-intro paths, last-touched dates, partnership status, and interaction sentiment.
  • Lookalikes — accounts whose profile, follower overlap, and content signals match users or partners but who haven't yet engaged. Ranked by ICP fit.

Each entry holds: handle, resolved identity, classification, score, source events, last interaction, projected next-best-action, and a list of edges (warm intros, mutual followers, shared partner orgs).

How the graph is built

Three analysis skills run on cron and write to the graph. They don't propose actions — only update what's known.

  • bd.audience-analyzer (daily) — reads marketing post events + reactor profiles, enriches each handle (bio, follower overlap, what they post about), updates user/partner classification.
  • bd.partner-lookalikes (weekly) — for each user/partner cohort, queries x-api for handles with overlapping followers and similar topic vectors. Scores by ICP fit. Stages new candidates with provenance ("matches the cohort that includes Vincent Wang and Jordi Alexander").
  • bd.partner-graph (weekly) — reads BD episodic memory (every interaction with every partner contact) and builds a graph of relationships, warm-intro paths, last-touched dates, sentiment scores. Writes the partner table and the partner-graph edge table.

Why the graph matters

Without it, Oslo treats every signal in isolation. A reaction on a tweet would just be a reaction. With the graph, the same reaction means "the COO of a partner protocol just liked this thread about haUSD" — and that's a different signal entirely.

Every other unit reads the graph. Marketing's marketing.suggest-content references which audience tier it's writing for. BD's bd.suggest-contacts ranks proposals by graph score. Ops' weekly brief surfaces partner-graph anomalies (someone who used to engage stopped engaging, someone new keeps showing up).

Note: The graph is shared company memory. Skills declare reads against audience_graph like any other memory; the capability token enforces it. Updates happen only via the analysis skills above. Skills cannot mutate the graph as a side effect.

4. Recommendations

Oslo doesn't only execute work. It also proposes work — what to do next, with reasoning. The recommendation queue is the output of weekly analysis skills that read the audience graph + recent activity + roadmap state, identify patterns, and surface proposals to Discord for operator review.

The proposal loop

Three unit-level proposal skills run weekly on cron:

  • bd.suggest-contacts — produces a list of "contact these 5 people this week, here's why for each". Each entry includes: handle, classification (user / partner / lookalike), audience-graph score, the specific signal that triggered the proposal (recent activity, roadmap moment, warm path), and a draft opening line.
  • marketing.suggest-content — produces 5 post topics for the next 7 days. Each entry includes: hook, format (text / chart / video), target time, expected engagement range based on marketing.engagement_patterns, and rationale ("works on the user cohort, ties to the v2 roadmap shipping next week").
  • ops.suggest-priorities — produces a "this week, focus on these 3 things; defer these 2" call. Each entry includes: rationale, dependencies, projected outcome, and what gets blocked if it slips.

A cross-unit aggregator (ops.weekly-strategy-brief) composes all three into one Sunday-evening Discord post in #oslo-proposals. Monday morning the operator reviews it.

The operator review

Each proposal renders with three buttons in Discord: accept, reject, edit. Accepting fires the next skill (e.g., bd.draft-outreach for an accepted contact). Rejecting writes a "rejected, reason: …" entry to the decisions log. Editing opens a follow-up dialog where the operator can adjust args.

The decisions log is critical — it's how the analysis side learns what's good and what's not. Next week's bd.suggest-contacts reads last week's accept/reject pattern. If you keep rejecting "warm intro through @x because @x replied to a thread once," the analyzer downweights that signal.

Note: Proposals never fire actions automatically. Even with high confidence and operator approval, write actions go through the standard HITL flow with capability-token gating. The recommendation loop produces "what should happen" — the operator and the safety layer both decide whether it does.

5. Units

Recommendations are the output of the scoring system. Units are the departments that act on those recommendations.

The six units cover Oslo's full work surface, but they should all run the same selection logic: maximum result, minimum wasted effort.

  • BD — partners, target accounts, outreach, contact recommendations, why-now logic.
  • Marketing — content calendar, daily posts, reaction analysis, brand voice, distribution, winning formats. Also owns design (banner specs, brand kit, social graphics, visual identity) — design work is operationally tied to Marketing, so it lives there rather than as a separate unit. Sub-categorized into Conversion, Content, SEO, Paid, Measurement, Retention, Growth (pattern from coreyhaines31/marketingskills).
  • Engineering — protocol notes, technical explanations, vault checks, roadmap state, product milestones. Vaults sit inside Engineering because vault work is engineering work.
  • Security — watchlists, exploit monitoring, threat briefs, real-time on-chain alerts.
  • Ops — activity logs, weekly reports, market briefs, coordination, roadmap cadence.
  • Data — account scoring, ICP clustering, lookalikes, customer and partner segmentation. The unit other units read from when they need analytical rigor instead of operational action.

Each unit has a foundational <unit>.context skill loaded by every other skill in that unit. The context skill holds ICP, partner criteria, brand voice, protocol rules, roadmap priorities, scoring rubrics, and content heuristics. That is what lets Oslo explain not only what it wants to do, but why it thinks the move makes sense.

Skills live in a flat folder, named <unit>.<verb>. Filename, slash command, and ID are the same string. E.g. bd.daily-leads.skill.ts is invoked as /oslo bd.daily-leads.

Each skill declares: id, unit, description, triggers, inputs/outputs (zod schemas), reads/writes/connectors, depends_on (other skills it composes with), hitl (human-in-the-loop flag), plan/act/verify (three-phase structure for write skills, with checkpointing between phases), and tests (at least three golden cases — happy path, edge case, adversarial input).

Worked example: bd.daily-leads

{
  id: 'bd.partner-lookalikes',
  unit: 'bd',
  description: 'Analyze engaged partner accounts, find lookalikes, rank who to contact next',
  triggers: ['who should we contact', 'find more like this', 'new partner leads'],
  inputs:  { sourceAccounts: Account[], limit: number, default: 25 },
  outputs: { accounts: Account[], reasons: string[], summary: string },
  reads:   ['bd.semantic', 'marketing.episodic', 'data.semantic', 'global'],
  writes:  ['bd.semantic', 'bd.episodic', 'data.working'],
  connectors: ['supabase', 'x-api', 'harmonix-brain', 'address-reputation'],
  depends_on: ['bd.context', 'data.audience-score'],
  hitl:    false,
  run:     async (ctx, { limit }) => { ... },
  tests:   [happyPath, sparseSignals, malformedProfile],
}

Plan → Act → Verify (with checkpointing)

Every write-skill is structured in three phases. plan describes what will be done, why, and to whom — pure, no side effects. act executes the plan; side effects happen here. verify checks the result — failures roll back act where possible. Each phase is a checkpoint. If verify fails or the process crashes, the skill resumes from the last checkpoint instead of restarting. Read-only skills can collapse to a single run.

Composition (not handoffs)

Skills compose: ops.weekly-report calls bd.daily-leads, gets a list, then calls marketing.calendar-snapshot with that list as context. The calling skill stays in charge. Composition primitives (.then(), .branch(), .parallel()) come from Mastra workflows, already in the runtime.

Consolidation skills

Each unit has a daily consolidate skill that reads episodic memory and updates procedural memory. Marketing's "hooks that worked" extends from posts above an engagement threshold. BD's "who replies and why" extends from live conversation outcomes. Data's "lookalike patterns" extends from which segments convert into users, partners, or meaningful conversations. Episodic grows; procedural improves; the system gets more useful from its own work.

Default safety: every read runs unattended, every write asks first. A skill that drafts an outreach DM runs free. A skill that sends the DM pauses for approval. Per-skill overrides are supported; the default sets the floor.

Note: Skills can call other skills. ops.weekly-report reads from BD's pipeline, Marketing's calendar, Engineering's vault marks, and Security's watchlist by composing the underlying skills, not by querying shared tables. Composition is explicit. A new report adds a new skill, not a new database query.

6. Memory

Memory is attached to units, but Oslo also maintains a shared operating graph. BD's leads should not blindly reach Marketing's prompts, and Engineering's vault marks should not bleed into Security's watchlist — but Oslo does need one place to answer higher-order questions like who our users are, who our partners are, who looks like them, what shipped last week, and what content moved the right audience.

Each unit has five memory types:

  • Audience graph — the shared company graph of users, partners, and lookalikes (Section 3). Read by every unit; written only by Data and BD analysis skills.
  • Semantic — what the unit knows. Leads, target accounts, audience segments, roadmap state, vault theses, watchlists, brand kit specs. Lives in Supabase, prefixed by unit.
  • Episodic — what happened. Outreach sent, posts published, reactions received, meetings held, alerts fired. Lives in Supabase with vector embeddings (numerical fingerprints of text, used to find similar past events by meaning rather than keyword match).
  • Procedural — how the unit works. Playbooks, prompts, templates, scoring rubrics, contact heuristics, content heuristics. Lives as markdown in units/<unit>/knowledge/. Version-controlled. The daily consolidate skill extends procedural memory from successful episodic patterns.
  • Working — what's active right now. In-flight drafts, today's queue, pending replies, top accounts to contact, roadmap-linked content ideas. Lives in Supabase with a TTL ("time to live" — auto-deletes after a set window).

Worked example: BD's directory

src/units/bd/
  knowledge/                   # procedural — markdown
    icp.md
    outreach-templates.md
    scoring-rubric.md
    objection-handling.md
  memory/
    semantic.ts                # bd_leads, bd_accounts → Supabase
    episodic.ts                # bd_events → Supabase + vector
    working.ts                 # bd_queue → Supabase with TTL
  decisions.md                 # the "why" log
  consolidate.skill.ts         # daily: episodic → procedural

Global memory and multi-agent contracts

One memory store sits outside the units: global memory. It holds Harmonix-wide context plus context exposed by external agent systems Oslo connects to. In practice, this becomes the audience graph and company graph: the merged view of accounts, relationships, roadmap state, and external signals that every unit can reason against through declared reads.

Each external system is reached through the open Agent2Agent (A2A) protocol — a standard hosted by the Linux Foundation, supported by Microsoft, Google, and AWS. Each external system publishes an Agent Card (JSON metadata describing its identity, skills, endpoint, auth). Oslo's connector reads the Agent Card and calls the documented skills. Either side can run on different machines, change stack, or be replaced — only the contract has to hold. This is the foundation for multi-agent collaboration as the protocol scales.

Decisions log

Each unit also keeps a decisions log — a markdown file recording the reason behind judgment calls. E.g. "Paused outreach to Acme because they raised; revisit Q4." Episodic memory captures what happened. The decisions log captures what was decided and why. The log is also where the recommendation loop closes — every accept / reject of a proposal lands here with the reason, and next week's analysis reads the log to adjust scoring weights.

Note: Skills compose across units, but they cannot bypass the rules. A weekly digest does not query BD's table directly; it asks BD's skill for the data, with the read explicitly declared and the capability token verifying it.

7. Connectors

Connectors are how Oslo touches anything outside its own process. Every external API, Supabase, Hyperliquid, X, Discord, Telegram, Notion, GitHub, app analytics, plus the LLM connector, is wrapped in a typed client that handles retry, rate limiting, caching, identity resolution, and cost tracking. Skills do not make raw HTTP calls. They go through ctx.connectors.<name>, and every call is checked against the skill's capability token before it is made. Connectors are structured as published packages with hot reload (pattern from Activepieces) so skills, the runtime, and any future marketplace can install them uniformly.

Capability tokens as the safety primitive

The capability token issued by dispatch is the foundation of the safety layer. Every memory access and connector call presents the token; anything outside what the token allows is rejected at the boundary, before the call is even attempted. Token is short-lived (expires when the skill finishes), scoped to a single skill run, and includes the actor on whose behalf the skill runs.

On top of the token, eighteen symptom-triggered rules fire automatically based on what the skill is doing. Six are distinctive enough to call out:

  • llm-endpoint-safety — scans every prompt for injection patterns and every output for leaked PII.
  • output-voice-check — for outputs going to public surfaces (X, Discord channels, DMs), a small judging model rates the output 1–5 against the unit's voice and claim guidelines. Below threshold, output is held for review.
  • cross-unit-read-policy — enforced via the capability token. A Marketing skill cannot read BD's working memory unless its token includes bd.working.
  • cost-and-rate-cap — each skill has a daily dollar cap and a per-minute call limit. Breach the cap and the skill auto-pauses.
  • dead-man-switch — global halt that trips when anomaly thresholds breach. All skills stop until cleared.
  • secret-egress-scan — every output checked for patterns matching any secret loaded into the runtime.

Each rule declares severity. block halts the skill and surfaces it for review; warn logs and continues. The full eighteen rules are in src/safety/rules/ in the (private) oslo repo.

The Hyperliquid trade guard

Hyperliquid is the only connector where Oslo can write to a chain. Because a single bad call has irreversible cost, the trade guard adds ten rules on top of the standard layer (the tenth is pre-flight transaction simulation, inspired by Hypernative's Guardian product). Four worth detailing:

  • Per-trade size cap. Every order checked against a hardcoded ceiling. Even with HITL approval, an order over the cap is rejected at the connector. Changing the cap requires a code commit.
  • Pre-flight simulation. Before sending, the connector simulates the trade and rejects if outcome diverges from the plan or if expected slippage exceeds threshold (e.g., 0.5%). Stops fat-finger orders, stale quotes, and thin-book moments.
  • Two-step + 60-second window. A trade approval doesn't fire the order; it enqueues it. Sixty seconds later, the connector asks for a second confirmation. Only then does it send.
  • Echo-back confirmation. When the second approval is requested, Oslo restates the order in full — {asset, side, size, expected fill, slippage, position after} — and asks for a code phrase, not just "y". Defeats accidental confirmations.

The remaining six (volume cap, asset whitelist, position cap, time-window guard, circuit breaker, address-reputation pre-check) are in src/safety/rules/hyperliquid-trade-guard.ts.

Note: Connectors are the only path Oslo has to anything outside its own process. There are no manual HTTP calls in skill code. Every external interaction is forced through one of two dozen typed methods, each gated by capability-token verification and wrapped by symptom-triggered rules. Skills cannot bypass safety because there is no path that does so.

6. Closing Loop

signal arrives → dispatch normalizes it → the audience graph classifies and enriches it → the system scores who matters and why → the right unit gets a recommendation → the operator approves or edits when needed → action is taken → the result is logged back into memory

That is the loop. Observe, score, prioritize, act, learn. The same idea should apply to growth, engineering, and ops. A small team should not try to outwork a much bigger team. It should out-select it.

Three voices

Operator
"I drive Oslo from Codex, Claude Code, Discord, or Telegram. Same skills, same memory, same safety rules whichever I use. Every irreversible action waits for me to confirm. The system gets better at my work the longer it runs because it remembers what worked and what didn't."
Unit
"I keep my own memory and my own playbooks. Other units don't read my data without declaring the read. I don't read theirs without declaring it either. Every day, my consolidate skill turns recent events into updated playbooks, so the procedural knowledge I expose stays current."
External Agent
"I'm a separate system from Oslo. We're connected by an A2A contract — read-only or read/write, defined by both sides via published Agent Cards. We don't share a database. Either of us can move to a different machine, change our internal stack, or be replaced. Only the contract has to hold. As more agent systems come online, this is how we'll coordinate."

How it scales

Oslo is built deliberately small at the start. The architecture supports three additive scaling phases — none requires rewriting what already works.

Phase 1 — The runtime (in progress)

Skills are scaffolded; the runtime that makes them callable is what we're building now: dispatcher, work queue, capability tokens, the safety layer, the connector wrappers, and the memory layer. CLI entry point first (every skill invocable from a terminal), then the MCP server (stdio mode), then the Discord and Telegram bots. The seven day-one skills become real work, one unit at a time.

Phase 2 — Multi-surface depth

Each unit grows from one skill to ten or twenty (BD pulls from coreyhaines/marketingskills as a reference shape). The eval harness with replay-against-prod becomes the default merge gate for any prompt or skill change. The Hyperliquid trade guard ships with all ten rules including the pre-flight simulation. Langfuse traces every run; the daily activity log writes itself.

Phase 3 — Hosted and multi-agent

Oslo moves from one laptop to a hosted service. The actor field already on every input becomes meaningful — anyone the team grants access can drive Oslo from any of the four entry points. Two-way A2A contracts let Oslo and external agent systems exchange messages, not just read each other's state. The skill format becomes portable enough to share with the Harmonix ecosystem; partner protocols run their own variants of bd.daily-leads and marketing.daily-post-draft against their own data.

Out of scope, by design

Hyperliquid auto-execute is not on the roadmap. Reads, drafts, paper trades, and simulations are supported. Automated execution of real orders without a human in the loop is not, and will not be. The trade guard exists to bound what HITL can approve, not to replace HITL.

Oslo today is a working operator scaffold. Oslo at the end of Phase 1 runs the seven day-one skills end-to-end. Oslo at v2 has the eval loop and the bot surfaces. Oslo at v3 talks to other agent systems as peers via A2A.
