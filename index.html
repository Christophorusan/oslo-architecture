Understanding AI Agents with Harmonix

Signals · Audience Graph · Recommendations · Units & Skills · Memory · Connectors

An AI agent that helps a small team run a company like a bigger one. It watches what's happening, decides what matters, acts on the right thing, and gets better at all of it over time.

Architecture Spec

Oslo is built from memory, skills, unit workflows, automation loops, and a feedback loop. It watches what's happening in the company, decides what matters, acts on the right thing, writes the result back to memory, and uses that result to do better next time.

The point is not to automate everything. It's to pick the right thing to do. A small team can't outwork a big one. It can out-select one. Oslo helps you decide who to talk to, what to post, what to ship, what to drop, and what to do tomorrow. It finds leads, suggests improvements, writes reports, drafts content, and gets sharper over time from the work it already did.

Three layers do most of the work. They blur together if you don't separate them:

Memory
What Oslo knows. Customers, partners, product, contacts, history, what worked, what didn't, how the team operates.
Skills
What Oslo can do. Reusable company workflows with typed inputs and outputs that get better from repeated use.
Units
Who owns the work. Six departments — BD, Marketing, Engineering, Security, Ops, Data — each running its own daily loop.

The split matters. Memory knows who the partner is. The skill knows how to score them and how to reach out. The BD unit owns that workflow. Same call, three different layers doing three different jobs.

Team members extend Oslo by adding new skills. The more skills the company teaches it, the more useful it gets — new workflows, new playbooks, new operating habits, all reusable.

Oslo runs online, like a protocol. People connect to it through Codex, Claude Code, Discord, and Telegram. All four reach the same dispatcher. Dispatch doesn't just pick a skill. It captures the signal, classifies it, enriches it, scores it, and routes it to the right unit. The unit runs Plan → Act → Verify, streams progress back, and writes the result to memory so the next run starts smarter.

Two paths into Oslo, depending on where the request comes from:

Codex / Claude Code
The host model is already in the loop. It reads your input, emits a structured tool call, and Oslo runs the skill. No extra routing.
Chat surface (Discord, Telegram, reactions, cron)
No host model upstream. Oslo's dispatcher does the routing itself through a deterministic ladder, falling back to a small LLM only when the input is genuinely new.

Why not put an LLM in front of every dispatch like other agent frameworks? Because two LLMs in series — host model plus dispatcher LLM — would do the work twice.

Oslo also talks to other agent systems. External agents connect through the open Agent2Agent (A2A) protocol hosted by the Linux Foundation, supported by Microsoft, Google, and AWS. Oslo never copies their state. The two systems share a contract, not a database.

Long term, Oslo should live online like a protocol-like company agent. The runtime stays private, but the system persists over time and team members connect to it through Claude Code, Codex, Discord, and Telegram.

Oslo's architecture has two layers. The data plane is the path every request takes: signal → classification → recommendation → unit action → memory update. The control plane is the configuration the data plane reads from on every request: a versioned skill registry, prompt registry, connector catalog, eval harness, and feature flags. Data plane runs constantly; control plane is loaded at boot and hot-reloaded on change. Detailed in Section 2 (Dispatch), since dispatch is the heaviest reader.

1. Signals

Signals are what Oslo watches. They tell you if the company is winning, where the value is coming from, and where attention should go next. The five that matter most are revenue, deposits, withdrawals, conversion, and retention. Everything else exists to explain those numbers better. Some signals come from operators driving Oslo directly. Others come from the world — a post gets a reply, a user deposits, a cron job fires. All signals reach the same dispatcher.

What Oslo watches

Five buckets, ordered by leverage:

  • Business outcomes — revenue, deposits, withdrawals, conversion, retention. The top of the watch list. Everything else exists to explain these.
  • Audience movement — X reactions on @harmonixfi (likes, replies, reposts, quotes), follower deltas, power-user activity (deposits, withdrawals, app sessions, vault usage), integration-partner movement (TVL shifts, ship moments worth reacting to), mentions across X / Discord / Telegram.
  • Product state — vault marks (PnL on positions), roadmap items shipping / blocked / slipping, GitHub PRs and deploys, incidents, feature usage from product analytics.
  • External world — Hyperliquid ecosystem moves (HYPE price, new vaults, integrations), crypto narrative shifts, security signals (exploits, audits, watchlist alerts), competitor moves.
  • Operator + feedback signals — @oslo commands from Discord / Telegram / Codex / Claude Code, cron triggers, webhooks, and every accept / reject / edit / postpone on past proposals. The decisions log is what makes the system get smarter.

Long-running handling is async-first: dispatch returns a job_id immediately and streams results back as they happen. A ninety-second skill does not block the IDE or the chat.

Operator-driven signals

Two of these come with their own model loaded — the host model in your coding agent does the natural-language interpretation. The other two are chat surfaces with no upstream model.

Claude Code is from Anthropic; Codex is from OpenAI. Different host models, same role to Oslo.

Codex — e.g. oslo bd.daily-leads --limit=50 from a terminal. Scripted runs, automation, scheduled jobs.

Claude Code — Oslo's tools appear in your coding session via an MCP server (Model Context Protocol — a standard interface for AI assistants to call external tools). Stdio for local mode, HTTP/SSE for hosted. Multi-step work where you want to read along.

Discord — slash command in a channel or @mention. Work that belongs in a shared log: outreach drafts, weekly briefs, anything the team should see.

Telegram — message the bot in plain language. Quick checks and phone approvals.

Non-operator signals

Signals that wake the dispatcher without a human typing:

  • X reactions — every like, reply, repost, quote on @harmonixfi posts. Treated as audience-graph and content-performance input.
  • App activity — deposits, withdrawals, vault interactions on the Harmonix app. Treated as user-classification, conversion, and retention input.
  • Cron — scheduled timer (default UTC, per-skill timezone override). Daily and weekly skills run on cron.
  • Webhooks — URLs external services POST to when something happens (Stripe payment, GitHub PR merged, partner-side event).
  • Replay — re-run a past trace_id, optionally with a different model, prompt, or skill version. Used for debugging and prompt regression testing.

Note: Whether typed by a human or fired by a timer, every signal gets normalized into the same shape and handed to dispatch. The unit running at the other end never has to know where the signal came from.

Dispatch and classification

Once a signal arrives, dispatch turns it into a typed skill call. No business logic — only routing, validation, classification, capability-token issuance, and logging.

A request moves through six steps: Parse (normalize input into a structured shape) → Classify (user, partner, prospect, noise, roadmap signal) → Resolve (pick a skill via the 4-tier fallback) → Validate (check args against the skill's typed schema using zod) → Confirm (ask if confidence is low or the skill writes externally) → Run (issue a capability token, enqueue, execute, stream results back).

Every input gets three IDs at parse time: trace_id (random, follows the request through every layer, replayable later), idempotency_key (deterministic, deduplicates retries), and capability_token (issued at run time, enumerates exactly what the skill can read, write, and call — checked at every boundary).

What classification adds

The Classify step is what makes dispatch more than a router. Before any skill runs, the dispatcher answers: who or what is this signal about? An X reaction goes through identity resolution — does the handle match a known user, a known partner contact, a lookalike candidate, a power user, a tourist, or a stranger? An app event matches against the user table and gets weighted by deposit size and retained capital. A roadmap webhook matches against the current roadmap state. Classification writes its result onto the input itself, so by the time a skill receives the call, it already knows whether the signal is high-priority (a known partner replying or a high-value user depositing size) or background noise (a bot retweet or a tourist). Skills do not reclassify — they trust the dispatcher's output.

What dispatch reads from the control plane

Dispatch is the heaviest reader of the control plane — the configuration the data plane consults but never writes to. On every request, dispatch reads from five components:

  • Skill Registry (versioned) — every skill the runtime knows about, with version numbers. Old versions stay queryable so replay can re-run any historical skill against any past input.
  • Prompt Registry — every LLM prompt named and versioned, separate from skill code. Editing a prompt does not require a redeploy. Prompt rollback is one revert away.
  • Connector Catalog — every external API connector available to skills, with declared cost, rate limit, and current health status. The catalog rejects skills that request connectors not present (or currently unhealthy).
  • Eval Harness — golden-test runner. Every skill ships with at least three test cases; CI runs the full suite on every change. Replay can also re-run last week's prod traffic against any new skill or prompt version and diff outputs — no skill or prompt change ships without this gate passing.
  • Cost + Token Telemetry — every skill and workflow records token usage, latency, model choice, and dollar cost so the system can optimize for efficiency as well as quality.
  • Feature Flags — turn skills on/off, route a percentage of traffic to a canary version, gate experimental connectors.

Keeping the two planes separate matters because the data plane needs to be fast and stable; the control plane needs to be flexible and frequently updated. Mixing them — hardcoded prompts inside skill code, connector configs scattered across files, no eval gate — is what turns small agent prototypes into systems no one can change without breaking.

The 4-tier resolver

Cheapest-first. Most inputs resolve without an LLM call.

  1. Slash — e.g. /oslo bd.daily-leads maps direct to skill ID.
  2. Channel + tag — e.g. @oslo refresh leads in #bd narrows to BD skills.
  3. Lunr index — keyword search over skill descriptions and triggers, deterministic.
  4. Small-model classifier — a small fast model returns {skill_id, args, confidence}. Free-tier inference is enough for routing; we don't burn paid frontier calls on classification. Below threshold → confirm-and-edit.

Streaming back

Skill progress events stream to the originating entry point as they happen — Discord typing indicator, Telegram message edits, Codex stdout, Claude Code partial MCP responses. The operator can also call oslo status <job_id> from any entry point or list active jobs with oslo jobs.

Note: When you drive Oslo from Codex or Claude Code, dispatch is trivial — the host model has already produced a structured tool call. The deterministic ladder (tier 1 / tier 2 / tier 3, with LLM fallback at tier 4) exists for chat surfaces (Discord, Telegram) where there is no host model upstream. Other agent frameworks (OpenAI Agents, Microsoft Agent Framework, LangGraph) put an LLM at the front of every dispatch regardless of source — for Oslo, that would mean running two LLMs in series (host model + dispatcher LLM) when one has already done the work.

2. Audience Graph

The audience graph is where signals become useful. Dispatch normalizes the event. This layer decides whether the account behind it is a power user, a tourist, an integration partner, a lookalike, or noise. It enriches the profile, links it to similar accounts, and writes the result back to memory.

The job here is selection, not volume. Oslo scores which people matter, which roadmap moment they are closest to, and which opportunities deserve attention this week. Without the graph, every signal looks the same. With it, a like on a tweet might mean nothing — or it might mean a partner protocol's COO just engaged with a thread about haUSD.

Four primary classifications, plus a graph of relationships between them:

  • Power users — the small set of users that produce most of the value. Identity-resolved across surfaces — the same person can have a handle on X, a wallet on chain, a Discord ID, a Telegram ID, and Oslo merges them. The strongest user-quality signals are large deposits and leaving those deposits in over time. Everything else (app sessions, withdrawals, reactions) helps explain those two.
  • Tourists — accounts that touch the protocol but do not retain capital. Small deposits, fast withdrawals, low session depth. Useful as a contrast set; not a target. The graph should bias hard toward power users and away from tourists.
  • Integration partners — growth and integration partners that can move real numbers for us. Think Superform or Clearstar. The strongest partner signal is the ability to bring TVL, users, transactions, revenue, deposits, and MAU. The graph tracks warm-intro paths, last-touched dates, partnership status, and interaction sentiment.
  • Lookalikes — accounts whose profile, follower overlap, and on-chain or content signals resemble power users or integration partners but have not yet engaged. Ranked by ICP fit.

Each entry holds: handle, resolved identity, classification, score, source events, last interaction, projected next-best-action, and a list of edges (warm intros, mutual followers, shared partner orgs).

How the graph is built

Three analysis skills run on cron and write to the graph. They do not propose actions — only update what is known. On top of that, Oslo should run a daily research loop that looks for new information, proposes updates to the graph and memory, and writes accepted changes back into the system.

  • bd.audience-analyzer (daily) — reads marketing post events + reactor profiles, enriches each handle (bio, follower overlap, what they post about), updates user/partner classification.
  • bd.partner-lookalikes (weekly) — for each user/partner cohort, queries x-api for handles with overlapping followers and similar topic vectors. Scores by ICP fit. Stages new candidates with provenance ("matches the cohort that includes Vincent Wang and Jordi Alexander").
  • bd.partner-graph (weekly) — reads BD episodic memory (every interaction with every partner contact) and builds a graph of relationships, warm-intro paths, last-touched dates, sentiment scores. Writes the partner table and the partner-graph edge table.

Why the graph matters

Without it, Oslo treats every signal in isolation. A reaction on a tweet would just be a reaction. With the graph, the same reaction means "the COO of an integration partner just liked this thread about haUSD" — and that's a different signal entirely.

Every other unit reads the graph. Marketing's marketing.suggest-content references which audience tier it's writing for. BD's bd.suggest-contacts ranks proposals by graph score and biases toward power users + integration partners. Ops' weekly brief surfaces partner-graph anomalies (a power user who used to deposit stopped depositing, an integration partner who used to push volume slowed down, a new lookalike keeps showing up).

Note: The graph is shared company memory. Skills declare reads against audience_graph like any other memory; the capability token enforces it. Updates happen only via the analysis skills above. Skills cannot mutate the graph as a side effect.

3. Recommendations

Oslo doesn't just execute work. It proposes work — what to do next, and why. The recommendation queue is the output of analysis skills that read the audience graph, recent activity, and roadmap state, find patterns, and post proposals to Discord for operator review.

The daily brief

Every morning, Oslo posts one short brief with the five calls that matter today:

  • Top power users to watch — who deposited, who's quiet, who's at risk of leaving.
  • Top integration partners to push — who can move TVL, users, transactions, revenue, deposits, MAU.
  • Top content idea for the day — the one post most likely to land with the right audience.
  • Top funnel / ops issue hurting growth — the bottleneck most worth fixing today.
  • Top improvement Oslo itself should make — the one change that would make the system more useful tomorrow.

The proposal loop

Three unit-level proposal skills feed the brief and run on cron:

  • bd.suggest-contacts — produces a list of "contact these 5 people, here's why for each", biased toward power users and integration partners. Each entry includes: handle, classification (power user / integration partner / lookalike), audience-graph score, the specific signal that triggered the proposal (recent activity, roadmap moment, warm path), and a draft opening line.
  • marketing.suggest-content — produces post topics for the next 7 days. Each entry includes: hook, format (text / chart / video), target time, expected engagement range based on marketing.engagement_patterns, and rationale ("works on the power-user cohort, ties to the v2 roadmap shipping next week").
  • ops.suggest-priorities — produces a "focus on these 3 things; defer these 2" call. Each entry includes: rationale, dependencies, projected outcome, and what gets blocked if it slips.

The weekly strategy brief

Sunday evening, a cross-unit aggregator (ops.weekly-strategy-brief) runs the three suggest skills in parallel, packages the output, and posts one digest to #oslo-proposals. Monday morning the operator reviews it. Daily brief is for today's calls. Weekly brief is for next week's posture: which partners to go after, which content arcs to plan, which roadmap items get the focus.

What every recommendation looks like

The point is not to output ranked lists. It is to make decisions legible — so the operator can approve, reject, edit, or postpone with full context, without having to dig. Every proposal — daily or weekly — renders in the same five-field shape:

  • What — the action being proposed.
  • Why — the reason it's the right move now.
  • Evidence — the specific signals from memory that support it (deposit size, retention curve, partner reach, last-touched date, content performance).
  • Suggested action — the next step Oslo would take if approved (draft DM, schedule post, open issue).
  • Confidence — how sure Oslo is, with the threshold that downgrades it to confirm-and-edit instead of accept-as-is.

The operator review

Each proposal renders with four buttons in Discord: accept, reject, edit, postpone. Accepting fires the next skill (e.g., bd.draft-outreach for an accepted contact). Rejecting writes a "rejected, reason: …" entry to the decisions log. Editing opens a follow-up dialog where the operator can adjust args. Postponing parks the proposal for a later cycle (default: next morning's brief) without dropping the context — the next run sees it again with fresh evidence and updated confidence.

The operator is the human loop. Their job is to review, steer, correct, approve, and improve the system over time. At minimum, the operator should be responsible for approving important actions, correcting bad recommendations, and improving the AI itself.

The decisions log is critical — it's how the analysis side learns what's good and what's not. Next week's bd.suggest-contacts reads last week's accept/reject pattern. If you keep rejecting "warm intro through @x because @x replied to a thread once," the analyzer downweights that signal.

Note: Proposals never fire actions automatically. Even with high confidence and operator approval, write actions go through the standard HITL flow with capability-token gating. The recommendation loop produces "what should happen" — the operator and the safety layer both decide whether it does. Oslo should never send important external messages, make financial or trading actions, change strategy or memory in a major way, publish outputs on its own, or make information public on its own without approval.

4. Units & Skills

Recommendations are the output of the scoring system. Skills are how the work gets done. Units are who owns it. Same call, three different layers.

Skills: reusable company workflows

A skill is a capability, a repeatable job, and most importantly a repeatable workflow. Not a one-off script. Not a prompt. A reusable company workflow that has:

  • Clear input (typed schema, validated at dispatch)
  • Clear output (typed schema, validated before return)
  • Defined memory reads/writes (which tables/graphs it touches)
  • Defined connectors (which external surfaces it can call)
  • A unit owner (the department responsible for it)
  • A way to improve over time (golden tests, replay against prod traffic, decisions-log feedback)

And every skill encodes three things, not just one:

  • How we do the task — the procedure, the prompts, the heuristics, the order of operations.
  • How we judge success — what counts as a good output, what counts as a bad one, the threshold for confirm-and-edit.
  • How the workflow gets better from repeated use — what the daily consolidate skill harvests, what the decisions log feeds back, how scoring weights shift week to week.

That's the difference between a script and a skill:

Script
Runs the same way every time. No memory. No feedback. Predictable input, predictable output. If the world changes, the script doesn't notice.
Skill
Learns the company's way of doing the job. Reads memory, writes memory, tracks cost and outcome. Improves week over week as accept/reject decisions feed back into scoring. The next run starts from a smarter place.

Units: who owns the work

The six units cover Oslo's full work surface, but they should all run the same selection logic: maximum result, minimum wasted effort. Each unit owns its own memory, its own skills, its own goals, and a daily research loop that keeps it current and in sync with the other departments.

  • BD — partners, target accounts, outreach, contact recommendations, why-now logic. Daily job: identify top integration partners, suggest who to contact, explain why now, and keep the partner graph current.
  • Marketing — content calendar, daily posts, reaction analysis, brand voice, distribution, winning formats. Also owns design (banner specs, brand kit, social graphics, visual identity) — design work is operationally tied to Marketing, so it lives there rather than as a separate unit. Daily job: track customer conversation, log what content worked, and keep the picture current of who customers are and what they are talking about.
  • Engineering — protocol notes, technical explanations, vault checks, roadmap state, product milestones. Vaults sit inside Engineering because vault work is engineering work. Daily job: track roadmap progress and surface blockers hurting adoption.
  • Security — watchlists, exploit monitoring, threat briefs, real-time on-chain alerts. Daily job: track trust and risk signals that could affect users or partners.
  • Ops — activity logs, weekly reports, market briefs, coordination, roadmap cadence. Daily job: identify bottlenecks, keep departments in sync, and make sure every unit sees what the others are doing and how they are performing.
  • Data — account scoring, ICP clustering, lookalikes, customer and partner segmentation. The unit other units read from when they need analytical rigor instead of operational action. Daily job: refresh scoring, detect pattern changes, and keep every unit aligned on the latest picture.

Each unit has a foundational <unit>.context skill loaded by every other skill in that unit. The context skill holds ICP, partner criteria, brand voice, protocol rules, roadmap priorities, scoring rubrics, and content heuristics. The daily research loop is what lets Oslo explain not only what it wants to do, but why it thinks the move makes sense — and what changed since yesterday that made it the right call.

Memory · Skills · Units, on one call

The three layers do different jobs on the same request. Take BD outreach to a partner:

  • Memory knows who the partner is — name, role, AUM, integrations, last interaction, classification, score.
  • The skill knows how to score and contact them — read the partner row, look up the warm path, draft the right opener, decide if it needs HITL.
  • The BD unit owns that workflow — sets the ICP, defines what counts as a good outreach, runs the daily research loop, reviews the proposals.

Easy to blur in conversation. Worth keeping crisp in the architecture: knowledge, capability, ownership.

How skills are declared

Skills live in a flat folder, named <unit>.<verb>. Filename, slash command, and ID are the same string. E.g. bd.daily-leads.skill.ts is invoked as /oslo bd.daily-leads.

Each skill declares: id, unit, description, triggers, inputs/outputs (zod schemas), reads/writes/connectors, depends_on (other skills it composes with), hitl (human-in-the-loop flag), plan/act/verify (three-phase structure for write skills, with checkpointing between phases), and tests (at least three golden cases — happy path, edge case, adversarial input).

Worked example: bd.partner-lookalikes

{
  id: 'bd.partner-lookalikes',
  unit: 'bd',
  description: 'Analyze engaged partner accounts, find lookalikes, rank who to contact next',
  triggers: ['who should we contact', 'find more like this', 'new partner leads'],
  inputs:  { sourceAccounts: Account[], limit: number, default: 25 },
  outputs: { accounts: Account[], reasons: string[], summary: string },
  reads:   ['bd.semantic', 'marketing.episodic', 'data.semantic', 'global'],
  writes:  ['bd.semantic', 'bd.episodic', 'data.working'],
  connectors: ['supabase', 'x-api', 'harmonix-brain', 'address-reputation'],
  depends_on: ['bd.context', 'data.audience-score'],
  hitl:    false,
  run:     async (ctx, { limit }) => { ... },
  tests:   [happyPath, sparseSignals, malformedProfile],
}

Plan → Act → Verify (with checkpointing)

Every write-skill is structured in three phases. plan describes what will be done, why, and to whom — pure, no side effects. act executes the plan; side effects happen here. verify checks the result — failures roll back act where possible. Each phase is a checkpoint. If verify fails or the process crashes, the skill resumes from the last checkpoint instead of restarting. Read-only skills can collapse to a single run.

Composition (not handoffs)

Skills compose: ops.weekly-report calls bd.daily-leads, gets a list, then calls marketing.calendar-snapshot with that list as context. The calling skill stays in charge. Composition primitives (.then(), .branch(), .parallel()) come from Mastra workflows, already in the runtime.

Consolidation skills

Each unit has a daily consolidate skill that reads episodic memory and updates procedural memory. Marketing's "hooks that worked" extends from posts above an engagement threshold. BD's "who replies and why" extends from live conversation outcomes. Data's "lookalike patterns" extends from which segments convert into users, partners, or meaningful conversations. Episodic grows; procedural improves; the system gets more useful from its own work. Every unit should also run a daily research pass so it stays current and in sync with the other departments.

Default safety: every read runs unattended, every write asks first. A skill that drafts an outreach DM runs free. A skill that sends the DM pauses for approval. Per-skill overrides are supported; the default sets the floor.

Note: Skills can call other skills. ops.weekly-report reads from BD's pipeline, Marketing's calendar, Engineering's vault marks, and Security's watchlist by composing the underlying skills, not by querying shared tables. Composition is explicit. A new report adds a new skill, not a new database query.

5. Memory

Memory is the company context layer. It's what makes Oslo more than a script that runs the same way every time. Memory remembers:

  • who customers are
  • who partners are
  • what the product is
  • who the key contacts are
  • what happened before
  • what content worked
  • what did not work
  • how the team likes to operate

Marketing memory adds two more: what customers are talking about and how content performed across surfaces. Unit memory stays scoped, but Oslo also maintains a shared operating graph so it can answer higher-order questions like who our best users are, which partners resemble them, what shipped last week, and what content or outreach actually moved the right audience.

Today, past, future

Memory should answer three temporal questions, not just one:

  • What matters today — working memory + the audience-graph snapshot. Active proposals, top accounts to reach this week, the roadmap items shipping now.
  • What mattered in the past — episodic memory + the decisions log. What worked, what didn't, what got rejected and why.
  • What will matter in the future — roadmap state, partner pipelines, content calendars, projected outcomes attached to accepted proposals. The forward-looking layer that lets today's choice account for what's coming.

The feedback loop reads all three. A recommendation that ignores the past is naïve. One that ignores the future is short-sighted. One that ignores today is irrelevant.

Memory types per unit

Each unit has five memory types:

  • Audience graph — the shared company graph of users, partners, and lookalikes (Section 3). Read by every unit; written only by Data and BD analysis skills.
  • Semantic — what the unit knows. Leads, target accounts, audience segments, roadmap state, vault theses, watchlists, brand kit specs. Lives in Supabase, prefixed by unit.
  • Episodic — what happened. Outreach sent, posts published, reactions received, meetings held, alerts fired. Lives in Supabase with vector embeddings (numerical fingerprints of text, used to find similar past events by meaning rather than keyword match).
  • Procedural — how the unit works. Playbooks, prompts, templates, scoring rubrics, contact heuristics, content heuristics. Lives as markdown in units/<unit>/knowledge/. Version-controlled. The daily consolidate skill extends procedural memory from successful episodic patterns.
  • Working — what's active right now. In-flight drafts, today's queue, pending replies, top accounts to contact, roadmap-linked content ideas. Lives in Supabase with a TTL ("time to live" — auto-deletes after a set window).

    icp.md
    outreach-templates.md

    objection-handling.md

Global memory and multi-agent contracts

One memory store sits outside the units: global memory. It holds Harmonix-wide context plus context exposed by external agent systems Oslo connects to. In practice, this becomes the audience graph and company graph: the merged view of accounts, relationships, roadmap state, and external signals that every unit can reason against through declared reads.

Each external system is reached through the open Agent2Agent (A2A) protocol — a standard hosted by the Linux Foundation, supported by Microsoft, Google, and AWS. Each external system publishes an Agent Card (JSON metadata describing its identity, skills, endpoint, auth). Oslo's connector reads the Agent Card and calls the documented skills. Either side can run on different machines, change stack, or be replaced — only the contract has to hold. This is the foundation for multi-agent collaboration as the protocol scales.

Decisions log

Each unit also keeps a decisions log — a markdown file recording the reason behind judgment calls. E.g. "Paused outreach to Acme because they raised; revisit Q4." Episodic memory captures what happened. The decisions log captures what was decided and why. The log is also where the recommendation loop closes — every accept / reject of a proposal lands here with the reason, and next week's analysis reads the log to adjust scoring weights.

Note: Skills compose across units, but they cannot bypass the rules. A weekly digest does not query BD's table directly; it asks BD's skill for the data, with the read explicitly declared and the capability token verifying it.

6. Connectors

Connectors are how Oslo touches anything outside its own process. Skills don't make raw HTTP calls. They go through a typed connector that handles retry, rate limiting, caching, identity resolution, cost tracking, and capability-token checks. The top-priority connectors are:

  • X — audience, reactions, content distribution, partner conversations.
  • Supabase — the home of memory: semantic, episodic, working, audience graph, audit log.
  • Discord — the team's shared log + the surface where every recommendation lands for review.
  • GitHub — roadmap state, PRs, ship notes, the source of truth for what's actually changing.
  • Product analytics — deposits, withdrawals, conversion, retention. The signals that tell us if anything Oslo proposed actually worked.

Telegram stays important for partner and reply workflows. Hyperliquid, Notion, defillama, coingecko, harmonix-brain, and address-reputation round out the long tail.

Every external API plus the LLM connector is wrapped in a typed client that handles retry, rate limiting, caching, identity resolution, and cost tracking. Skills do not make raw HTTP calls. They go through ctx.connectors.<name>, and every call is checked against the skill's capability token before it is made. Connectors are structured as published packages with hot reload (pattern from Activepieces) so skills, the runtime, and any future marketplace can install them uniformly.

Capability tokens as the safety primitive

The capability token issued by dispatch is the foundation of the safety layer. Every memory access and connector call presents the token; anything outside what the token allows is rejected at the boundary, before the call is even attempted. Token is short-lived (expires when the skill finishes), scoped to a single skill run, and includes the actor on whose behalf the skill runs.

On top of the token, eighteen symptom-triggered rules fire automatically based on what the skill is doing. Six are distinctive enough to call out:

  • llm-endpoint-safety — scans every prompt for injection patterns and every output for leaked PII.
  • output-voice-check — for outputs going to public surfaces (X, Discord channels, DMs), a small judging model rates the output 1–5 against the unit's voice and claim guidelines. Below threshold, output is held for review.
  • cross-unit-read-policy — enforced via the capability token. A Marketing skill cannot read BD's working memory unless its token includes bd.working.
  • cost-and-rate-cap — each skill has a daily dollar cap and a per-minute call limit. Breach the cap and the skill auto-pauses.
  • dead-man-switch — global halt that trips when anomaly thresholds breach. All skills stop until cleared.
  • secret-egress-scan — every output checked for patterns matching any secret loaded into the runtime.

Each rule declares severity. block halts the skill and surfaces it for review; warn logs and continues. The full eighteen rules are in src/safety/rules/ in the (private) oslo repo.

The Hyperliquid trade guard

Hyperliquid is the only connector where Oslo can write to a chain. Because a single bad call has irreversible cost, the trade guard adds ten rules on top of the standard layer (the tenth is pre-flight transaction simulation, inspired by Hypernative's Guardian product). Four worth detailing:

  • Per-trade size cap. Every order checked against a hardcoded ceiling. Even with HITL approval, an order over the cap is rejected at the connector. Changing the cap requires a code commit.
  • Pre-flight simulation. Before sending, the connector simulates the trade and rejects if outcome diverges from the plan or if expected slippage exceeds threshold (e.g., 0.5%). Stops fat-finger orders, stale quotes, and thin-book moments.
  • Two-step + 60-second window. A trade approval doesn't fire the order; it enqueues it. Sixty seconds later, the connector asks for a second confirmation. Only then does it send.
  • Echo-back confirmation. When the second approval is requested, Oslo restates the order in full — {asset, side, size, expected fill, slippage, position after} — and asks for a code phrase, not just "y". Defeats accidental confirmations.

The remaining six (volume cap, asset whitelist, position cap, time-window guard, circuit breaker, address-reputation pre-check) are in src/safety/rules/hyperliquid-trade-guard.ts.

Cost + token efficiency

Every LLM call records tokens_in, tokens_out, model, cost_usd, and latency_ms to oslo_skill_calls, keyed by trace_id and skill_id. That gives you four rollups for free: cost per skill, cost per trace, cost per model, and cost per unit per day.

The point is not just to know the bill. It's to optimize. Oslo improves on quality and efficiency:

  • Use the cheapest path that does the job well. Default to a small free-tier model (Groq Llama 3.1-8b). Escalate to a larger model only when confidence is low, the task is high-stakes, or the output quality matters.
  • Compress context. Memory is reused, not re-explained. Procedural memory (markdown playbooks) sits in the system prompt once; episodic snippets are pulled by relevance, not dumped wholesale.
  • Avoid redundant reasoning. A skill that already classified an account doesn't reclassify it next time. Dispatch writes the classification onto the input so downstream skills trust it.
  • Cap per skill. Each skill has a daily dollar cap. Breach the cap and it auto-pauses until the next UTC day. Stops a runaway prompt from burning the whole budget.

The ops.cost-report skill rolls all of this up over a day, week, or month. oslo.suggest-self-improvement reads the same data and proposes which skill to cheap-tier next — that's the 5th slot in the daily morning brief.

Note: Connectors are the only path Oslo has to anything outside its own process. There are no manual HTTP calls in skill code. Every external interaction is forced through one of two dozen typed methods, each gated by capability-token verification and wrapped by symptom-triggered rules. Skills cannot bypass safety because there is no path that does so.

Closing Loop

signal→dispatch normalizes→audience graph classifies + enriches→system scores who matters and why→unit gets a recommendation→operator approves / edits / postpones→action is taken→result logged to memory→next signal starts smarter

That's the loop. Observe, score, prioritize, act, learn.

The feedback loop isn't just the last box. It sits over the whole system. It improves memory, skills, automation, unit strategy, and the recommendations themselves. It learns from business outcomes, not engagement. If a post leads to a deposit, that matters more than likes. If an outreach leads to retention, that matters more than a reply. If a partner conversation leads to measurable TVL, that matters more than the meeting count.

Over time, Oslo gets better at three things: self-improvement, sharper suggestions, and higher conversion. Every accept, reject, edit, and postpone feeds back into the scoring. Every deposit, withdrawal, and retention event feeds back into who counts as a power user. Every shipped roadmap item feeds back into what content actually moved the audience. A small team can't outwork a big one. It can out-select one.

Three voices

Operator
"I drive Oslo from Codex, Claude Code, Discord, or Telegram. Same skills, same memory, same safety rules whichever I use. Every irreversible action waits for me to confirm. The system gets better at my work the longer it runs because it remembers what worked and what didn't."
Unit
"I keep my own memory and my own playbooks. Other units don't read my data without declaring the read. I don't read theirs without declaring it either. Every day, my consolidate skill turns recent events into updated playbooks, so the procedural knowledge I expose stays current."
External Agent
"I'm a separate system from Oslo. We're connected by an A2A contract — read-only or read/write, defined by both sides via published Agent Cards. We don't share a database. Either of us can move to a different machine, change our internal stack, or be replaced. Only the contract has to hold. As more agent systems come online, this is how we'll coordinate."

How it scales

Oslo is built deliberately small at the start. The architecture supports three additive scaling phases — none requires rewriting what already works.

Phase 1 — The runtime (in progress)

Skills are scaffolded; the runtime that makes them callable is what we're building now: dispatcher, work queue, capability tokens, the safety layer, the connector wrappers, and the memory layer. CLI entry point first (every skill invocable from a terminal), then the MCP server (stdio mode), then the Discord and Telegram bots. The seven day-one skills become real work, one unit at a time.

Phase 2 — Multi-surface depth

Each unit grows from one skill to ten or twenty (BD pulls from coreyhaines/marketingskills as a reference shape). The eval harness with replay-against-prod becomes the default merge gate for any prompt or skill change. The Hyperliquid trade guard ships with all ten rules including the pre-flight simulation. Langfuse traces every run; the daily activity log writes itself.

Phase 3 — Hosted and multi-agent

Oslo moves from one laptop to a hosted service. The actor field already on every input becomes meaningful — anyone the team grants access can drive Oslo from any of the four entry points. Two-way A2A contracts let Oslo and external agent systems exchange messages, not just read each other's state. The skill format becomes portable enough to share with the Harmonix ecosystem; partner protocols run their own variants of bd.daily-leads and marketing.daily-post-draft against their own data.

Out of scope, by design

Hyperliquid auto-execute is not on the roadmap. Reads, drafts, paper trades, and simulations are supported. Automated execution of real orders without a human in the loop is not, and will not be. The trade guard exists to bound what HITL can approve, not to replace HITL.

Oslo today is a working operator scaffold. Oslo at the end of Phase 1 runs the seven day-one skills end-to-end. Oslo at v2 has the eval loop and the bot surfaces. Oslo at v3 talks to other agent systems as peers via A2A.
