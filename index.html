Understanding AI Agents with Harmonix

10 layers · entry points · agent core · prompt + context · routing · connectors · execution · memory · audience + recommendations · units · feedback loop

An AI agent that helps a small team run a company like a bigger one. It watches what's happening, decides what matters, acts on the right thing, and gets better at all of it over time. The whole system is ten layers — each with one job, each readable in isolation.

One-line model

Oslo is a company agent that lives online, watches the signals that matter, routes them through shared memory and unit workflows, and returns a daily and weekly operating brief through interfaces like Codex, Claude Code, Discord, and Telegram.

The point is not to automate everything. It's to pick the right thing to do. A small team can't outwork a big one. It can out-select one. Oslo helps you decide who to talk to, what to post, what to ship, what to drop, and what to do tomorrow. It finds leads, suggests improvements, writes reports, drafts content, and gets sharper over time from the work it already did.

The cleanest way to think about it: one core agent loop, many entry points, ten layers. Each layer has one job. Each is readable on its own. Codex, Claude Code, Discord, Telegram, cron, and APIs all hit the same underlying brain. The messenger changes. Memory, skills, routing, and feedback do not.

Below the diagram, every layer is described twice — what it is in one line, then how it works as a short list of mechanics. The data plane (signal → classification → recommendation → unit action → memory update) runs on every request. The control plane (skill registry, prompt registry, connector catalog, eval harness, feature flags) is loaded at boot and hot-reloaded on change.

Three layers do most of the work. They blur together if you don't separate them:

Memory
What Oslo knows. Customers, partners, product, contacts, history, what worked, what didn't, how the team operates.
Skills
What Oslo can do. Reusable company workflows with typed inputs and outputs that get better from repeated use.
Units
Who owns the work. Six departments — BD, Marketing, Engineering, Security, Ops, Data — each running its own daily loop.

The split matters. Memory knows who the partner is. The skill knows how to score them and how to reach out. The BD unit owns that workflow. Same call, three different layers doing three different jobs.

Team members extend Oslo by adding new skills. The more skills the company teaches it, the more useful it gets — new workflows, new playbooks, new operating habits, all reusable. The best skills should become procedural memory: once the company figures out a non-trivial workflow, Oslo should be able to save it, improve it, and reuse it.

Oslo runs online, like a protocol. People connect to it through Codex, Claude Code, Discord, Telegram, cron, and APIs. All of them reach the same agent core through a thin gateway layer. Dispatch doesn't just pick a skill. It captures the signal, classifies it, enriches it, scores it, and routes it to the right unit. The unit runs Plan → Act → Verify, streams progress back, and writes the result to memory so the next run starts smarter.

Two paths into Oslo, depending on where the request comes from:

Codex / Claude Code
The host model is already in the loop. It reads your input, emits a structured tool call, and Oslo runs the skill. No extra routing.
Chat surface (Discord, Telegram, reactions, cron)
No host model upstream. Oslo's dispatcher does the routing itself through a deterministic ladder, falling back to a small LLM only when the input is genuinely new.

Why not put an LLM in front of every dispatch like other agent frameworks? Because two LLMs in series — host model plus dispatcher LLM — would do the work twice.

Oslo also talks to other agent systems. External agents connect through the open Agent2Agent (A2A) protocol hosted by the Linux Foundation, supported by Microsoft, Google, and AWS. Oslo never copies their state. The two systems share a contract, not a database.

Long term, Oslo should live online like a protocol-like company agent. The runtime stays private, but the system persists over time and team members connect to it through Claude Code, Codex, Discord, and Telegram.

1. Entry points

What it is. The doors into Oslo. Thin surfaces — they don't change the brain, only how the request arrives. The same agent core sits behind every one of them.

Components. Five surface types: Codex (host model in the terminal, scripted runs), Claude Code (host model in the IDE via MCP), Discord (chat surface, team channels), Telegram (chat surface, mobile + partners), Cron / API (scheduled timers, webhooks, replay).

How it works. The two host-model surfaces come with their own LLM upstream — the IDE produces a structured tool call and dispatch is trivial. The two chat surfaces have no host model, so the agent core's deterministic resolver does the routing itself (Layer 4). Cron, webhooks, and replay are non-operator signals: scheduled timers, external POSTs, re-runs of a past trace_id with a different model or prompt. Whether a human types or a timer fires, every signal is normalized into the same shape and handed to dispatch — the unit at the other end never has to know where it came from. Async-first: dispatch returns a job_id immediately and streams results back; a ninety-second skill never blocks the IDE or the chat.

Five buckets of signals enter through these doors, ordered by leverage:

  • Business outcomes — revenue, deposits, withdrawals, conversion, retention. The top of the watch list. Everything else exists to explain these.
  • Audience movement — X reactions on @harmonixfi, follower deltas, power-user activity, integration-partner movement, mentions across X / Discord / Telegram.
  • Product state — vault marks (PnL on positions), roadmap items shipping / blocked / slipping, GitHub PRs and deploys, incidents, feature usage from product analytics.
  • External world — Hyperliquid ecosystem moves, crypto narrative shifts, security signals (exploits, audits, watchlist alerts), competitor moves.
  • Operator + feedback signals — @oslo commands from Discord / Telegram / Codex / Claude Code, and every accept / reject / edit / postpone on past proposals. The decisions log is what makes the system get smarter.

2. Agent core

What it is. The shared conversation loop — one brain across every surface. Codex, Discord, Telegram, scheduled briefs all hit the same loop. The messenger changes, the loop doesn't.

Components. Six steps in order — parse → classify → resolve → validate → confirm → run — and three IDs stamped along the way: trace_id (random, follows every layer, replayable later), idempotency_key (deterministic hash, deduplicates retries), capability_token (issued at run, enumerates allowed reads / writes / connectors).

How it works. No business logic in the core — only routing, validation, classification, capability-token issuance, and logging. Parse normalizes input. Classify figures out who or what the signal is about. Resolve picks a skill via the 4-tier ladder. Validate checks args against the skill's typed schema. Confirm asks the operator if confidence is low or the skill writes externally. Run issues the capability token, enqueues, executes, streams results back.

Classification is what makes the core more than a router. Before any skill runs, it answers: who or what is this signal about? An X reaction goes through identity resolution — handle match against known user, partner, lookalike, power user, tourist, or stranger. An app event matches against the user table and gets weighted by deposit size and retained capital. A roadmap webhook matches against current roadmap state. Classification writes its result onto the input, so by the time a skill receives the call it already knows whether the signal is high-priority or background noise. Skills don't reclassify — they trust the core's output.

3. Prompt + context assembly

What it is. What Oslo actually sees before it reasons. The layer that takes everything we know and packs it into a single prompt sized for the model that will run.

Components. Six sources feed in. Public: system rules (constitution + tone), architecture context (this document). Private: team context (heuristics, playbooks). Scoped per-request: memory excerpts (pulled by relevance, capability-gated), attached skills (procedural memory that applies right now), tool list (only authorized connectors).

How it works. The public/private split matters. Architecture is shareable; the playbooks behind it are not. Both feed the prompt — only the former feeds the world. Memory isn't dumped wholesale; episodic snippets are pulled by relevance, procedural markdown sits in the system prompt once and stays there. The capability token from Layer 2 decides which memory tables this assembly is even allowed to read from in the first place — a Marketing skill cannot see BD's working memory unless its token includes bd.working.

4. Provider + routing layer

What it is. Decides which model handles which job. Balances quality, speed, token usage, and cost. The cheapest path that does the job well, with escalation when stakes rise.

Components. A 4-tier deterministic ladder for skill resolution on chat surfaces (slash, channel+tag, Lunr index, small classifier), plus two model paths underneath (small free-tier default, larger model on escalate), and per-call cost telemetry feeding daily caps.

How it works. Most inputs resolve without an LLM call — tiers 1-3 are deterministic. Tier 1 (slash) maps /oslo bd.daily-leads directly to a skill ID. Tier 2 (channel + tag) narrows to a unit's skills via @oslo refresh leads in #bd. Tier 3 (Lunr index) keyword-searches skill descriptions and triggers. Tier 4 (small classifier) is the only paid path — a free-tier model returns {skill_id, args, confidence}; below threshold, the system asks the operator to confirm. Once a skill is selected, the default execution model is small and free; escalation to a larger model fires only on low confidence, high stakes, or quality-sensitive output. Every call records tokens_in, tokens_out, model, cost_usd, latency_ms to oslo_skill_calls, keyed by trace_id and skill_id. Per-skill daily dollar caps; breach the cap and the skill auto-pauses until the next UTC day.

5. Tool + connector layer

What it is. How Oslo touches anything outside its own process. Skills don't make raw HTTP calls — they go through typed connectors gated by capability tokens and wrapped by safety rules.

Components. The capability token gate, five top connectors (X, Supabase, Discord, GitHub, product analytics), the long tail (Telegram, Notion, Hyperliquid, defillama, coingecko, harmonix-brain, address-reputation), the 18-rule safety belt, and the Hyperliquid trade guard (10 extra rules on the only chain-writing connector).

How it works. Every external API plus the LLM connector is wrapped in a typed client that handles retry, rate limiting, caching, identity resolution, and cost tracking. Skills call ctx.connectors.<name>; every call is checked against the skill's capability token before it's made. The capability token is short-lived (expires when the skill finishes), scoped to a single skill run, and includes the actor on whose behalf the skill runs. On top of the token, 18 symptom-triggered rules fire automatically based on what the skill is doing — severity is block (halt + ask) or warn (log + continue). Hyperliquid is the only connector where Oslo can write to a chain; the trade guard adds per-trade size cap, pre-flight transaction simulation, two-step + 60-second window, echo-back code phrase, asset whitelist, position cap, and address-reputation pre-check on top of the standard layer.

6. Execution backends

What it is. Where tools actually run. The connector above defines the contract; this layer is the substrate that fulfills it.

Components. Three substrates: local runtime (single laptop, sync calls — Phase 1 today), background queue (BullMQ / Inngest, for skills that take more than a few seconds — Phase 1-2), cloud / hosted (24/7 uptime — Phase 3). Plus a replay layer that lets any past trace_id re-run anywhere.

How it works. The interface stays identical even as the substrate changes — a skill that ran on your laptop yesterday can run in the cloud tomorrow without touching its caller. Long-running calls don't block the IDE or the chat surface; they return a job_id and stream progress back to the originating entry point. Replayability lives at this layer: any past trace can re-run on a different substrate, with a different model, against a different prompt version, and the outputs diffed against the original.

7. Memory layer

What it is. What Oslo knows. The temporal company context — what matters today, what mattered in the past, what's about to matter next.

Components. Three time horizons (today / past / future), two shared graphs (audience graph — power users, tourists, partners, lookalikes; global memory — A2A-connected external agents), and five per-unit types: semantic (facts), episodic (events, vector-embedded), procedural (markdown playbooks), working (TTL'd queue), decisions log (why-this-why-not).

How it works. Memory should answer three temporal questions, not just one. Today = working memory + audience-graph snapshot. Past = episodic + decisions log. Future = roadmap state, partner pipelines, content calendars, projected outcomes. A recommendation that ignores the past is naïve, one that ignores the future is short-sighted, one that ignores today is irrelevant. Memory is curated, not dumped: durable facts, successful workflows, decision reasons in; raw noise, duplicate entries, prompt-like text out — rejected before they land. The capability token from Layer 2 enforces cross-unit reads. External agent systems plug in via the open Agent2Agent (A2A) protocol — they publish an Agent Card, Oslo reads it and calls the documented skills. Either side can move machines or replace stack — only the contract has to hold.

8. Audience + recommendation layer

What it is. Where Oslo decides who matters and what to do next. Not volume — selection. The audience graph classifies every account, scoring drives ranking, and the output is legible proposals an operator can approve in seconds.

Components. Four graph classifications (power users, tourists, integration partners, lookalikes), three analysis skills that build the graph on cron (bd.audience-analyzer daily, bd.partner-lookalikes + bd.partner-graph weekly), two briefs (daily morning + weekly strategy), one 5-field proposal shape (what / why / evidence / suggested action / confidence), four operator buttons (accept / reject / edit / postpone), and a repeat-rejected modal for low-cost candidate disambiguation.

How it works. The three analysis skills build the graph on cron — they don't propose actions, only update what's known. Without the graph, every signal looks the same. With it, a like means something specific. Every other unit reads the graph: Marketing's marketing.suggest-content references which audience tier it's writing for, BD's bd.suggest-contacts ranks proposals by graph score, Ops' weekly brief surfaces anomalies — a power user who stopped depositing, a partner that slowed, a lookalike that keeps showing up. Operator decisions feed the decisions log, which feeds Layer 10's weight skills. Repeat-rejected: second reject without a captured reason opens a modal — free-form reason, structured tags (out_of_icp, timing, already_engaged...), optional resurface date. Score gets multiplied by 0.3; the candidate stays in the pool with the prior reason attached as evidence on future proposals.

9. Unit workflows

What it is. Who owns the work. Six departments running the company in parallel — each with its own goals, memory, skills, and a daily research loop. The system acts like one company, not six separate bots.

Components. Six units: BD (partners, outreach, why-now logic), Marketing (content, reactions, design), Engineering (roadmap, vaults, ship notes), Security (watchlists, exploits, alerts), Ops (cadence, briefs, cross-unit sync), Data (scoring, ICP, lookalikes). Each has a foundational <unit>.context skill plus a daily <unit>.daily-research skill that runs on cron.

How it works. Each unit has a foundational <unit>.context skill loaded by every other skill in that unit — ICP, partner criteria, brand voice, protocol rules, scoring rubrics, content heuristics. Each unit also runs a daily-research skill on cron between 7:00–7:25 UTC (cheap, no LLM, pure aggregation), so the morning brief at 8:05 reads fresh status from every department. Recommendations are the output of the scoring system. Skills are how the work gets done. Units are who owns it. Same call, three different layers — knowledge, capability, ownership.

Skills: reusable company workflows

A skill is a capability, a repeatable job, and most importantly a repeatable workflow. Not a one-off script. Not a prompt. A reusable company workflow that has:

  • Clear input (typed schema, validated at dispatch)
  • Clear output (typed schema, validated before return)
  • Defined memory reads/writes (which tables/graphs it touches)
  • Defined connectors (which external surfaces it can call)
  • A unit owner (the department responsible for it)
  • A way to improve over time (golden tests, replay against prod traffic, decisions-log feedback)

The strongest Hermes-style idea to borrow here is that skills should become procedural memory. When Oslo or the team discovers a non-trivial workflow that works, it should not disappear into chat history. It should become a skill the system can call again, improve, and eventually route automatically.

And every skill encodes three things, not just one:

  • How we do the task — the procedure, the prompts, the heuristics, the order of operations.
  • How we judge success — what counts as a good output, what counts as a bad one, the threshold for confirm-and-edit.
  • How the workflow gets better from repeated use — what the daily consolidate skill harvests, what the decisions log feeds back, how scoring weights shift week to week.

That's the difference between a script and a skill:

Script
Runs the same way every time. No memory. No feedback. Predictable input, predictable output. If the world changes, the script doesn't notice.
Skill
Learns the company's way of doing the job. Reads memory, writes memory, tracks cost and outcome. Improves week over week as accept/reject decisions feed back into scoring. The next run starts from a smarter place.

Units: who owns the work

The six units cover Oslo's full work surface, but they should all run the same selection logic: maximum result, minimum wasted effort. Each unit owns its own memory, its own skills, its own goals, and a daily research loop that keeps it current and in sync with the other departments.

  • BD — partners, target accounts, outreach, contact recommendations, why-now logic. Daily job: identify top integration partners, suggest who to contact, explain why now, and keep the partner graph current.
  • Marketing — content calendar, daily posts, reaction analysis, brand voice, distribution, winning formats. Also owns design (banner specs, brand kit, social graphics, visual identity) — design work is operationally tied to Marketing, so it lives there rather than as a separate unit. Daily job: track customer conversation, log what content worked, and keep the picture current of who customers are and what they are talking about.
  • Engineering — protocol notes, technical explanations, vault checks, roadmap state, product milestones. Vaults sit inside Engineering because vault work is engineering work. Daily job: track roadmap progress and surface blockers hurting adoption.
  • Security — watchlists, exploit monitoring, threat briefs, real-time on-chain alerts. Daily job: track trust and risk signals that could affect users or partners.
  • Ops — activity logs, weekly reports, market briefs, coordination, roadmap cadence. Daily job: identify bottlenecks, keep departments in sync, and make sure every unit sees what the others are doing and how they are performing.
  • Data — account scoring, ICP clustering, lookalikes, customer and partner segmentation. The unit other units read from when they need analytical rigor instead of operational action. Daily job: refresh scoring, detect pattern changes, and keep every unit aligned on the latest picture.

Each unit has a foundational <unit>.context skill loaded by every other skill in that unit. The context skill holds ICP, partner criteria, brand voice, protocol rules, roadmap priorities, scoring rubrics, and content heuristics. The daily research loop is what lets Oslo explain not only what it wants to do, but why it thinks the move makes sense — and what changed since yesterday that made it the right call.

Daily research, per unit

Every unit runs a <unit>.daily-research skill. Cheap, no LLM, pure aggregation. Cron schedules them between 7:00 and 7:25 UTC so the morning brief at 8:05 reads fresh status from every unit:

  • data.daily-research (7:00) — counts the audience graph by classification, computes top score movers up and down vs yesterday's snapshot, flags new high-value wallets from oslo_app_wallets.
  • sec.daily-research (7:05) — counts new watchlist entries, breaks down recent sec_events by severity, surfaces any critical alerts for the morning brief risk slot.
  • eng.daily-research (7:10) — counts shipped vs blocked roadmap items in the window, lists items past their target date that aren't done, reads vault PnL deltas, counts eng_events.
  • marketing.daily-research (7:15) — buckets the last 24h of posts by format and surface, finds the top engagement post, normalizes the average against oslo_market_state so a flat-day winner stays a winner.
  • ops.daily-research (7:20) — runs last so it sees what the others wrote. Scans every unit's events table, flags units that have been silent (might be stuck), counts skill failures from oslo_audit_log, identifies the day's bottleneck.

BD already had its daily skills (bd.daily-leads, bd.audience-analyzer) so it's not in this list. After this loop, every unit has a heartbeat — and the morning brief stops being only as fresh as the suggest-* skills.

Memory · Skills · Units, on one call

The three layers do different jobs on the same request. Take BD outreach to a partner:

  • Memory knows who the partner is — name, role, AUM, integrations, last interaction, classification, score.
  • The skill knows how to score and contact them — read the partner row, look up the warm path, draft the right opener, decide if it needs HITL.
  • The BD unit owns that workflow — sets the ICP, defines what counts as a good outreach, runs the daily research loop, reviews the proposals.

Easy to blur in conversation. Worth keeping crisp in the architecture: knowledge, capability, ownership.

How skills are declared

Skills live in a flat folder, named <unit>.<verb>. Filename, slash command, and ID are the same string. E.g. bd.daily-leads.skill.ts is invoked as /oslo bd.daily-leads.

Each skill declares: id, unit, description, triggers, inputs/outputs (zod schemas), reads/writes/connectors, depends_on (other skills it composes with), hitl (human-in-the-loop flag), plan/act/verify (three-phase structure for write skills, with checkpointing between phases), and tests (at least three golden cases — happy path, edge case, adversarial input).

Worked example: bd.partner-lookalikes

{
  id: 'bd.partner-lookalikes',
  unit: 'bd',
  description: 'Analyze engaged partner accounts, find lookalikes, rank who to contact next',
  triggers: ['who should we contact', 'find more like this', 'new partner leads'],
  inputs:  { sourceAccounts: Account[], limit: number, default: 25 },
  outputs: { accounts: Account[], reasons: string[], summary: string },
  reads:   ['bd.semantic', 'marketing.episodic', 'data.semantic', 'global'],
  writes:  ['bd.semantic', 'bd.episodic', 'data.working'],
  connectors: ['supabase', 'x-api', 'harmonix-brain', 'address-reputation'],
  depends_on: ['bd.context', 'data.audience-score'],
  hitl:    false,
  run:     async (ctx, { limit }) => { ... },
  tests:   [happyPath, sparseSignals, malformedProfile],
}

Plan → Act → Verify (with checkpointing)

Every write-skill is structured in three phases. plan describes what will be done, why, and to whom — pure, no side effects. act executes the plan; side effects happen here. verify checks the result — failures roll back act where possible. Each phase is a checkpoint. If verify fails or the process crashes, the skill resumes from the last checkpoint instead of restarting. Read-only skills can collapse to a single run.

Composition (not handoffs)

Skills compose: ops.weekly-report calls bd.daily-leads, gets a list, then calls marketing.calendar-snapshot with that list as context. The calling skill stays in charge. Composition primitives (.then(), .branch(), .parallel()) come from Mastra workflows, already in the runtime.

Consolidation skills

Each unit has a daily consolidate skill that reads episodic memory and updates procedural memory. Marketing's "hooks that worked" extends from posts above an engagement threshold. BD's "who replies and why" extends from live conversation outcomes. Data's "lookalike patterns" extends from which segments convert into users, partners, or meaningful conversations. Episodic grows; procedural improves; the system gets more useful from its own work. Every unit should also run a daily research pass so it stays current and in sync with the other departments.

Default safety: every read runs unattended, every write asks first. A skill that drafts an outreach DM runs free. A skill that sends the DM pauses for approval. Per-skill overrides are supported; the default sets the floor.

Note: Skills can call other skills. ops.weekly-report reads from BD's pipeline, Marketing's calendar, Engineering's vault marks, and Security's watchlist by composing the underlying skills, not by querying shared tables. Composition is explicit. A new report adds a new skill, not a new database query.

10. Feedback + research loop

What it is. What makes Oslo compound. This layer sits over the whole system — improving signals, scores, recommendations, memory, and skills based on real outcomes, not engagement.

Components. Two weight skills (data.weight-decisions reads accept/reject patterns, data.weight-outcomes joins on-chain results), two outcome data skills (data.app-activity-sync nightly + data.market-snapshot hourly), per-unit daily research, full replayability on any past trace_id, and a self-improvement skill that proposes which prompt or skill to revise next.

How it works. Learn from outcomes, not engagement — a post that drives a deposit matters more than likes; an outreach that drives retention matters more than a reply. data.weight-decisions runs weekly, reads 28 days of accept/reject/postpone, computes per-signal accept rate, writes weights. data.weight-outcomes reads 7-30 day accepted proposals, joins against on-chain activity (oslo_app_wallets) and market-adjusted content performance (via oslo_market_state), combines with the decisions side via geometric mean. The merged weight is what suggest-* skills read on the next run. Replayability lets the team re-run any past trace against a new model, prompt, or skill version and diff outputs. The full loop on every request:

signal→core normalizes→audience graph classifies + enriches→system scores who matters and why→unit gets a recommendation→operator approves / edits / postpones→action is taken→result logged to memory→next signal starts smarter

Two weight-skills run every week to feed scoring back into the system. Two outcome-skills feed real on-chain activity into the same loop:

That's the loop. Observe, score, prioritize, act, learn. Over time, Oslo gets better at three things: self-improvement, sharper suggestions, and higher conversion. Every accept, reject, edit, and postpone feeds back into scoring. Every deposit, withdrawal, and retention event feeds back into who counts as a power user. Every shipped roadmap item feeds back into what content actually moved the audience. A small team can't outwork a big one. It can out-select one.

How "outcome" is measured (with real data)

data.app-activity-sync
Nightly. Scans every Harmonix vault contract on HyperEVM (haHYPE, hakHYPE, haUSDC) and Arbitrum (BasisTrade) for ERC20 deposit and withdraw events. Aggregates to oslo_app_activity (per wallet × day × vault) and oslo_app_wallets (per wallet rollup: total deposited, days active, classification). Source of truth for "did money move".
data.market-snapshot
Hourly. Captures HYPE / BTC / ETH price + 24h change, Hyperliquid 24h volume, Harmonix TVL. Writes to oslo_market_state. Lets the outcome evaluator normalize: "a post that got 80 likes on a -8% HYPE day is stronger than the same 80 likes on a +5% pump day."

So when a BD proposal is accepted and the @user behind it deposits to a Harmonix vault within 14 days, data.weight-outcomes joins oslo_app_wallets.linked_handle against oslo_app_activity, sees the deposit, and credits the signals that supported the proposal. When a marketing post is judged, the engagement number is divided by a market-adjustment multiplier — a flat-day winner stays a winner; a pump-day winner gets adjusted down.

Repeat-rejected candidates: ask, don't discard

Suppose Oslo keeps recommending @vincent because his audience-graph score is high and the learned weights still favor him, but you reject him every week. Two of the three options are wrong:

  • (a) keep showing him with no change — wastes your attention.
  • (b) auto-suppress after N rejects — discards a candidate who might still be good once a missing piece of context resolves.
  • (c) ask why, redo the score, keep him in the pool with adjusted weight — the operator's call.

So that's what Oslo does. On the second reject of the same target without a captured reason, Discord opens a modal: "Why isn't @vincent a fit?" Three fields: free-form reason, structured tags (out_of_icp, timing, already_engaged, wrong_signal, low_priority, needs_warm_intro, not_now_revisit), optional resurface date. The reason persists in oslo_target_feedback. On the next run, score gets multiplied by 0.3 and the proposal carries the prior reason as evidence. The candidate is never deleted from the pool. The score adjusts. The reason stays in memory. The system learns by being asked, not by being silent.

The loop closes itself. Decisions feed weights. Outcomes feed weights. Operator feedback feeds weights. Weights feed scoring. Scoring feeds decisions. The system gets sharper from the work it already did.

Three voices

Operator
"I drive Oslo from Codex, Claude Code, Discord, or Telegram. Same skills, same memory, same safety rules whichever I use. Every irreversible action waits for me to confirm. The system gets better at my work the longer it runs because it remembers what worked and what didn't."
Unit
"I keep my own memory and my own playbooks. Other units don't read my data without declaring the read. I don't read theirs without declaring it either. Every day, my consolidate skill turns recent events into updated playbooks, so the procedural knowledge I expose stays current."
External Agent
"I'm a separate system from Oslo. We're connected by an A2A contract — read-only or read/write, defined by both sides via published Agent Cards. We don't share a database. Either of us can move to a different machine, change our internal stack, or be replaced. Only the contract has to hold. As more agent systems come online, this is how we'll coordinate."

How it scales

Oslo is built deliberately small at the start. The architecture supports three additive scaling phases — none requires rewriting what already works.

It should scale in three directions at once: more surfaces, better memory, and cheaper execution. The key is that the core loop stays the same while the entry points, skills, and connectors multiply around it.

Phase 1 — The runtime (in progress)

Skills are scaffolded; the runtime that makes them callable is what we're building now: one shared agent core, dispatcher, work queue, capability tokens, the safety layer, the connector wrappers, and the memory layer. CLI entry point first (every skill invocable from a terminal), then the MCP server (stdio mode), then the Discord and Telegram bots. The seven day-one skills become real work, one unit at a time.

Phase 2 — Multi-surface depth

Each unit grows from one skill to ten or twenty (BD pulls from coreyhaines/marketingskills as a reference shape). The eval harness with replay-against-prod becomes the default merge gate for any prompt or skill change. Memory safety rules and curated memory writes become strict defaults. The Hyperliquid trade guard ships with all ten rules including the pre-flight simulation. Langfuse traces every run; the daily activity log writes itself.

Phase 3 — Hosted and multi-agent

Oslo moves from one laptop to a hosted service. The actor field already on every input becomes meaningful — anyone the team grants access can drive Oslo from any of the entry points. Two-way A2A contracts let Oslo and external agent systems exchange messages, not just read each other's state. Replayable traces, session routing, and portable skills make the system shareable enough that partner protocols can run their own variants of bd.daily-leads and marketing.daily-post-draft against their own data.

Out of scope, by design

Hyperliquid auto-execute is not on the roadmap. Reads, drafts, paper trades, and simulations are supported. Automated execution of real orders without a human in the loop is not, and will not be. The trade guard exists to bound what HITL can approve, not to replace HITL.

Oslo today is a working operator scaffold. Oslo at the end of Phase 1 runs the seven day-one skills end-to-end. Oslo at v2 has the eval loop and the bot surfaces. Oslo at v3 talks to other agent systems as peers via A2A.
