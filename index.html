Oslo Backend Protocol

Technical documentation for the Harmonix growth engine: ingestion, signal normalization, wallet lead scoring, lifecycle memory, Discord review, and measurement. The system is designed as a backend protocol for growth operations, not an autonomous outbound bot.

01

Core concepts

The nouns in the backend: sources, signals, leads, lifecycle profiles, review cards, and outcomes.

Oslo should expose its growth logic like protocol documentation: every object has an owner, an input path, a write contract, and an output. The first production goal is holder lead onboarding for HYPE, kHYPE, USDC, and Harmonix vault users.

01SourceAny upstream feed: X, HyperEVM logs, vault state, Discord notes, BD notes, market research.
02SignalA normalized observation with evidence, timestamp, confidence, and next action.
03LeadA wallet, account, person, or organization worth reviewing for onboarding or retention.
04Lifecycle profileThe current stage and history of a lead or user segment.
05Review cardA Discord-ready approval unit: evidence, recommendation, risk, and owner.
06OutcomeThe result after human action: approved, rejected, replied, met, deposited, retained, expanded.

Backend architecture

Composable layers from ingestion to review. Each layer is clickable and openable.
The architecture mirrors protocol-doc structure: clear components, explicit contracts, and operational constraints.

Converts raw events into typed, deduplicated, evidence-backed records.

Writes outcomes back into the system so the next run has memory.

03

Data contracts

The tables and fields that make Oslo measurable instead of conversational.
3.1

holder_leads

Wallet-level lead records for HYPE, kHYPE, USDC, and vault behavior.

migration 035
  • Required: wallet, chain, asset_exposure, last_seen_at, score, score_reason, source, status.
  • Do not publish balances publicly. Use internal review only.
3.2

lead_signals

Evidence records attached to leads, accounts, and lifecycle profiles.

migration 035
  • Required: entity_id, signal_type, observed_at, evidence, confidence, created_by_skill.
  • Signal types include holder, allocator, reply opportunity, risk, retention, expansion.
3.3

lifecycle_profiles

Current stage, owner, next step, and segment memory for users or leads.

migration 036
  • Stages: discover, qualify, onboard, activate, habit, expand, retain, win_back.
  • Every transition should include a reason and source signal.
3.4

lifecycle_messages

Drafted internal or external touchpoints with approval state.

migration 036
  • Required: profile_id, channel, draft_body, approval_status, reviewer, sent_at.
  • External sends require approval. No autonomous outbound.
3.5

x_source_health

Tracks whether X ingestion is healthy or falling back to alternate sources.

migration 035
  • Required: source, status, checked_at, error_code, fallback_used, notes.
  • Used by marketing.x-performance-audit to keep reports honest.

05

Interfaces

Where data enters, where decisions happen, and where state is stored.
  • readHyperEVM RPC logs for holder and vault activity.
  • readX API, RSS, and fallback sources for public attention signals.
  • readBrain documents for operating truth and strategy.
  • writeSupabase tables for normalized leads, signals, lifecycle profiles, and source health.
  • writeInternal Discord reports and review cards.
  • manualHuman approval before X, Telegram, Discord, email, or BD outreach.
  • futureOslo web app dashboard for review queues, segments, and outcomes.
  • futureOlson web UI merge after the Mac Olson runtime is preserved.
06

Safety controls

Protocol constraints for privacy, compliance, and operational quality.
  • controlNo automatic X, Telegram, Discord, or email DMs.
  • controlNo public wallet balance disclosure. Wallet intelligence stays internal.
  • controlEvery lead card requires evidence, score reason, suggested next action, and confidence.
  • controlEvery report includes blockers, weak signals, and missing data.
  • controlMac Oslo remains the production runtime. No VM bot and no credential copy.

Runbook

The next backend sequence to move from architecture to live holder onboarding.
01

Apply migrations

Apply 035_x_and_holder_lead_engine.sql and 036_lifecycle_marketing_operator.sql to production Supabase.

02

Patch holder ingestion

Replace the broken explorer path with chunked HyperEVM RPC log scans and normalized asset exposure records.

03

Run holder discovery

Score HYPE, kHYPE, USDC, and vault-linked wallets. Store reasons and evidence for every lead.

04

Post review queue

Send top lead cards and lifecycle blockers to internal Discord. Humans approve next action.

05

Write outcomes

Record approvals, replies, meetings, deposits, retention, and rejections so the next run improves.
