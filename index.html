An AI agent that helps a small team run a company like a bigger one. It watches what's happening, decides what matters, acts on the right thing, and gets better at all of it over time. The whole system is ten layers — each with one job, each readable in isolation.

What Oslo is

Oslo is a company agent. It watches what's happening, decides what matters, runs the work, and learns from results.

Many ways to reach it; one brain underneath. Ten layers, each with one job. Read on for what each does and how they connect.

1. Entry points

Five ways to reach Oslo: Codex, Claude Code, Discord, Telegram, or scheduled jobs. All five hit the same brain. The messenger changes; what's underneath doesn't.

Whether a person types or a timer fires, every request is normalized into the same shape before anything else happens. Slow jobs return a ticket and stream progress back — they don't block the IDE or the chat.

2. Agent core

The single loop that runs every request. Six steps, every time: read the input, figure out what it's about, pick the right skill, check the inputs, confirm if unsure, run.

The core only routes and tracks — no business logic lives here. The figure-out-what-it's-about step is what makes it useful: by the time a skill receives a request, it already knows whether the signal is high-priority or background noise.

read→ classify→ pick skill→ check inputs→ confirm→ run

3. Prompt + context

What Oslo reads before it thinks. Six sources merge into one prompt: rules and tone, the public architecture, private team playbooks, scoped memory, the active skill, and only the tools the request is allowed to call.

Public stays shareable, private never leaves. Memory is pulled by relevance, not dumped wholesale.

4. Routing

Which model handles which job. Cheap by default; bigger model only when stakes are high or the answer is unclear.

Most chat requests resolve without any model call at all — a slash command, a tag in a channel, or a keyword match is enough. The model only steps in when those fail. Every call's cost gets tracked, and each skill has a daily spend cap.

5. Tools and connectors

Everything outside Oslo's process: X, Supabase, Discord, GitHub, Hyperliquid, and the rest. Skills don't make raw API calls — every external call goes through a typed wrapper that checks permission before firing and gets wrapped by safety rules.

Hyperliquid is the only path that touches a chain. It gets ten extra checks: trade size cap, pre-flight simulation, two-step confirmation with a code phrase, address reputation check, and more.

There are no manual HTTP calls in skill code. Every external interaction is forced through one of two dozen typed methods, each gated by capability-token verification and wrapped by symptom-triggered rules. Skills cannot bypass safety because there is no path that does so.

6. Where it runs

Today: your laptop. Soon: a background queue so slow jobs don't block. Later: hosted in the cloud. The skill stays the same; only the substrate changes.

Any past request can be replayed somewhere else against a new prompt or model and the outputs compared.

7. Memory

What Oslo knows. Three time horizons — what matters today (active queue), what mattered in the past (events + decisions), what's coming next (roadmap, pipelines, plans).

Each team has its own memory; shared maps of customers, partners, and external agents sit on top. Memory is curated, not dumped — raw noise gets rejected before it lands.

8. Who matters, what to do

Selection, not volume. Every account gets sorted into four buckets: power users, tourists, partners, lookalikes. From there, Oslo builds a daily brief — the five calls that matter today — and a weekly strategy brief for next week's posture.

Every proposal includes the same five things: what to do, why now, what evidence supports it, the suggested next step, and how confident Oslo is. You accept, reject, edit, or postpone. That's the learning signal.

9. Units

Six teams own the work: BD, marketing, engineering, security, ops, data. Each has its own goals, memory, skills, and a daily research pass.

Every morning each team checks in (7:00 to 7:20 UTC), so the 8:05 daily brief reads fresh status from every department.

10. Feedback loop

What makes Oslo compound. Sits over the whole system and learns from outcomes — a deposit, a retained user — not from engagement like likes.

Every accept and reject changes the next recommendation. Every deposit changes who counts as a power user. Any past request can be replayed against a new prompt or model to see what would have worked better. A small team can\'t outwork a big one — it can out-select one.

signal→brain reads→classify→score→recommend→you decide→act→log→next signal smarter
